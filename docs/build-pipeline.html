From a Lab idea to a running app

What happens after an idea is promoted and a build is started: how the brief and its approved prototype turn into a hosted, clickable application.

1

Promoted Lab idea

brief + prototype

A community-voted idea: four short brief fields (problem, audience, key features, title) plus an approved HTML prototype that fixes the visual target. Demand and design are validated before any code is written.

2

Assemble the build inputs

SPEC.md + TASKS.md

The backend composes two documents: a SPEC (the brief, a required-capabilities list, and the full prototype inlined as a visual contract) and an ordered TASKS plan. Both are size-checked before they leave.

3

Submit the job

POST /v1/jobs

The build service receives the app name, SPEC, TASKS, and target namespace, validates the input size, and queues the job. It then launches one isolated, single-use builder container on the host.

4

Builder container

runs each task in order

Every task moves through a five-stage agent pipeline. The active stage is highlighted as it cycles; the loop repeats for each task in the plan.

QUERY
Sonnet
Asks what it needs to know about the workspace.
›
RESEARCH
Sonnet
Reads the spec and existing files to gather context.
›
PLAN
Opus
Designs the implementation for this task.
›
BUILD
Opus
Writes the actual code.
›
AUDIT
Sonnet
Reviews its own work and fixes issues (the doubt loop).
QUERY → RESEARCH → PLAN → BUILD → AUDIT  ·  repeated per task

↻ backend polls progress every 15s → updates the page (10-95%)
5

Deploy the preview

isolated container

When the tasks pass, the service starts a separate preview container that serves the built application and returns a hosted URL.

6

Live application

clickable preview

The backend records the preview URL and the page swaps to "Open the built app". The idea is now a running application, served on its own subdomain.
