Many Hands,
One Ranch

What happens when the build loop learns to split the herd? Concurrent workstreams let multiple agents ride in parallel -- each on its own trail, all converging at the same railhead.

Context Foundry · Design Concept · March 2025

Context Foundry runs one task at a time through its four-stage pipeline: Scout, Plan, Implement, Doubt. One trail, one herd, one drive. That works for features that touch 5-15 files in a single area. But real projects have natural seams -- a backend API, a frontend UI, an infrastructure layer -- where the work is largely independent but needs to converge at a single railhead. Serial execution means your API wrangler sits idle while the frontend hand works, even though they could ride at the same time. For a project with three independent workstreams, you're paying 3x the wall-clock time for work that could overlap.

~:~=~:~=~:~=~:~=~:~=~:~

Why You Can't Just Run N Trail Drives

The naive approach -- "spin up three full SPID pipelines against the same ranch" -- does not work with Foundry's architecture. Three fences stand in the way:

One trail, one checkpoint chain. Foundry's build loop assumes a single .buildloop/current-plan.md, a single .buildloop/review-report.md, and one checkpoint chain per task. Peer loops would need a new orchestration layer, not just more folders. (context.rs, build.rs)

Existing parallelism is narrower than this proposal. Foundry can parallelize builder work today because it starts from one plan, splits explicit file operations, then merges by copying owned files back. That dual-builder model works because both builders follow the same plan and touch non-overlapping files. It does not generalize to api/ui/infra workstreams with semantic dependencies -- those need different plans, different contracts, and a fundamentally different merge strategy.

The hole is integration authority, not isolation. Git worktrees give you isolation for free. The hard problem is who owns the merge. Foundry's dual-pipeline mode already avoids auto-merging and leaves comparison to a human -- a deliberate design choice that signals long-lived parallel branches need a dedicated integrator, not a "merge everything at the end" hand.

The right model is not "N equal full loops." It is concurrent workstreams under one trail boss: one top-level architecture pass, bounded lanes for parallel work, a dedicated integration owner for shared files, and one system-level review at the end. This matches how Foundry already thinks -- curated artifacts, fresh contexts, isolated workers.

~:~=~:~=~:~=~:~=~:~=~:~

The Model

This is not "three full trail drives." It is one orchestrated cattle drive:

  1. One top-level scout ride -- Scout reads the full codebase. Decompose splits work and writes contracts.
  2. Bounded parallel lanes -- each workstream gets Plan + Implement only. No per-lane Scout (the territory was already surveyed). No per-lane Doubt (that happens at the railhead).
  3. A dedicated integration lane -- owns shared files (package.json, Cargo.toml, shared types, infra). Rebases and merges published artifacts at milestones, not just once at the end.
  4. One system-level Review -- a fresh-context inspector audits the integrated result. This is the only Doubt pass.

Foundry's core principle is one curated handoff chain with isolated contexts. This design preserves that: the trail boss hands off to lanes, lanes hand off to integration, integration hands off to review. At no point do multiple agents compete for truth over the same territory.

~:~=~:~=~:~=~:~=~:~=~:~

The Decompose Stage

After Scout reads the codebase, Decompose is the trail boss calling the shots. It does three things:

  1. Identifies natural seams. Where are the clean fence lines? An API layer and a UI layer communicating over HTTP. An infra layer provisioning what the app consumes. Decompose groups related work into lanes.
  2. Defines interface contracts. Before any lane starts building, contracts must exist. These are the shared types, API shapes, event formats, and config schemas that lanes on both sides of a boundary agree on.
  3. Assigns strict file ownership. Each lane gets an exclusive set of file paths. Shared files are owned only by the integration lane. No lane writes outside its owns set.

The output is a typed manifest -- JSON, not markdown -- matching Foundry's existing pattern of structured envelopes for design-time orchestration:

{
  "version": 1,
  "master_task": "T12",
  "master_plan": ".buildloop/master-plan.md",
  "shared_kernel_owner": "integration",
  "contracts": {
    "api_schema": {
      "file": "schemas/openapi.yaml",
      "owner": "api",
      "consumers": ["ui"]
    },
    "db_schema": {
      "file": "migrations/001_init.sql",
      "owner": "api",
      "consumers": ["integration"]
    }
  },
  "loops": {
    "api": {
      "status": "ready",
      "branch": "foundry/api",
      "owns": ["src/api/**", "schemas/openapi.yaml", "migrations/**"],
      "publishes": ["api_schema", "db_schema"],
      "blocks_on": []
    },
    "ui": {
      "status": "blocked",
      "branch": "foundry/ui",
      "owns": ["src/ui/**", "src/hooks/**", "src/pages/**"],
      "consumes": ["api_schema"],
      "blocks_on": ["api"]
    },
    "integration": {
      "status": "ready",
      "branch": "foundry/integration",
      "owns": [
        "package.json", "Cargo.toml", "tsconfig.json",
        "src/types/**", "infra/**", "docker-compose.yaml"
      ]
    }
  }
}

Key distinction: the manifest is JSON with a version field, and integration is a first-class lane that owns all shared files -- not an afterthought merge step at the end of the drive.

The Laws of the Range

These rules are enforced by the orchestrator, not by gentlemen's agreement:

  1. No lane writes outside owns. If a lane needs a file it doesn't own, it must declare a contract dependency, not reach across the fence.
  2. Shared files are owned only by integration. Package manifests, lockfiles, root config, shared type definitions -- one owner, zero ambiguity.
  3. Consumers depend on published artifacts, not live branches. When the api lane publishes openapi.yaml, the artifact is snapshotted. The ui lane receives that snapshot -- it does not read from api's live worktree.
  4. Integrate at milestones, not only at the end. The integration lane rebases and merges as contracts are published. Waiting until all lanes finish amplifies merge conflicts and delays failure detection.
  5. Start strict. v1 supports max 2-3 lanes. No nested lanes. No overlapping ownership. These constraints loosen once the orchestration layer is trail-proven.
Why no per-lane Doubt? Running full Scout/Plan/Doubt inside every lane is the wrong shape for this codebase. Foundry's design principle is one curated handoff chain with isolated contexts. Per-lane review duplicates work and creates competing sources of truth about what "correct" means. One system-level review pass with full integration context catches more than three narrow inspections ever could.

Interface Contracts

Contracts are the mechanism that makes parallel work converge. Without them, you get three hands all branding different marks on the same cattle.

A contract is a file that defines the shape of a boundary. It is written during Decompose, before any lane starts building. Both sides -- producer and consumer -- reference the same contract artifact.

Frozen contracts. Contract files are written once during Decompose and locked down. No lane may modify a contract during implementation. If a lane discovers the contract is wrong, it stops and escalates -- Decompose re-runs with updated information. This is expensive, by design. It forces the architect to get contracts right upfront rather than letting lanes silently drift.

Worktree Isolation

Each lane runs in its own git worktree on a dedicated branch. This gives every lane a full copy of the ranch where it can build, modify, and tear down without spooking the other herds.

.buildloop/
  loop-manifest.json       # typed coordination state
  master-plan.md           # human-readable architecture
  worktrees/
    api/                   # git worktree on branch foundry/api
      .buildloop/
        current-plan.md
        build-claims.md
    ui/                    # git worktree on branch foundry/ui
      .buildloop/
        current-plan.md
        build-claims.md
    integration/           # git worktree on branch foundry/integration
      .buildloop/
        current-plan.md    # plan for shared file changes
        merge-log.md       # record of milestone merges

Each worktree has its own plan and claims. The manifest lives in the main worktree. The integration lane's worktree is where milestone merges happen -- it pulls published artifacts from other lanes and resolves conflicts with full context about who owns what.

~:~=~:~=~:~=~:~=~:~=~:~

Execution Flow

1. SCOUT            single agent, reads the full territory
                     writes scout-report.md

2. DECOMPOSE        single agent, reads scout-report + task list
                     writes master-plan.md (human-readable)
                     writes loop-manifest.json (machine-readable)
                     writes contract files
                     creates worktrees and branches

3. PARALLEL LANES   orchestrator reads manifest:
                       for each lane where blocks_on is empty:
                         spawn agent in worktree
                         PLAN  -> current-plan.md
                         IMPLEMENT -> build-claims.md
                       when a lane publishes a contract:
                         snapshot artifact
                         update manifest status
                         unblock waiting lanes
                         integration lane rebases + merges

4. INTEGRATE        integration lane merges all branches
                     full build + test suite on merged result
                     conflict resolution with ownership context

5. REVIEW           single fresh-context agent
                     reads all build-claims, contract files, merged code
                     audits boundary correctness
                     fixes HIGH and MEDIUM issues
                     writes review-report.md

6. COMMIT           verified commit (or one per lane, squashed)

Step 3 is where the parallelism lives. But note: the integration lane is active throughout step 3, not just at the end. It merges published artifacts at each milestone, catching integration failures early rather than letting them pile up.

The Integration Lane

This is the most important design decision and the biggest departure from "just run N drives."

In Foundry's existing dual-builder mode, auto-merging is deliberately avoided. The comparison is left to a human. That design choice tells us something: when parallel agents produce divergent output, you need a dedicated authority to decide what the merged result looks like.

The integration lane is that authority:

  • Owns all shared files. Package manifests, lockfiles, root config, shared types, infrastructure definitions. These files have exactly one writer.
  • Merges at milestones. When the api lane publishes openapi.yaml, the integration lane immediately pulls that artifact and merges it into the integration branch. It does not wait for all lanes to finish.
  • Resolves conflicts with context. The integration agent has full knowledge of the manifest -- who owns what, what contracts exist, which files should never conflict. This context makes merge resolution deterministic rather than heuristic.
  • Runs build verification after each merge. Every milestone merge triggers a build check. If the api output breaks the shared types, the integration lane catches it before the ui lane even starts.
Integration is not Doubt. The integration lane does not audit claims or review code quality. It handles the mechanical and semantic work of merging parallel output into a coherent whole. Review happens once, after integration, with fresh eyes and full context.

Manifest as Coordination Protocol

The manifest replaces ad-hoc communication between agents with a structured protocol. The orchestrator watches it and reacts to state transitions:

FieldPurpose
versionSchema version for forward compatibility
master_taskParent task ID from TASKS.md
shared_kernel_ownerWhich lane owns shared files (always "integration" in v1)
contractsMap of contract ID to {file, owner, consumers}
loops[].statusready | implementing | published | blocked | failed
loops[].ownsGlob patterns -- exclusive file ownership
loops[].publishesContract IDs this lane produces
loops[].consumesContract IDs this lane depends on
loops[].blocks_onLane IDs that must reach "published" status first

Status transitions: ready -> implementing -> published (or failed). A lane moves to implementing when its agent spawns. It moves to published when it finishes and its artifacts are snapshotted. Blocked lanes watch for their dependencies to reach published.

When to Saddle Up

Concurrent workstreams add orchestration overhead. The question is whether the parallelism gains outrun that overhead.

Good fit

  • Projects with 2-3 independent workstreams and clear fence lines
  • Full-stack builds: API + frontend + infrastructure
  • Large builds where serial execution takes 30+ minutes wall-clock
  • Greenfield projects where contracts can be staked out upfront

Poor fit

  • Small features (under 10 files total) -- serial SPID is faster
  • Tightly coupled codebases where every change touches shared state
  • Refactoring work that crosses all boundaries simultaneously
  • Cases where existing dual-builder parallelism is sufficient
Rule of thumb: If you can draw clean fence lines around the work with narrow gates between them, workstreams will help. If everything depends on everything, stay serial. When in doubt, Foundry's existing dual-builder mode (two models, one plan, file-level splitting) covers the common case without the orchestration cost.

Open Questions

  • Contract evolution. Frozen contracts force the architect to get it right upfront. When that fails, the penalty is a full Decompose re-run. A lighter-weight amendment protocol -- where the owning lane can propose a contract change that consumers must ACK -- could reduce this cost without sacrificing safety.
  • Orchestrator complexity. Foundry's runtime today assumes one plan, one checkpoint chain. The orchestrator layer that watches the manifest, spawns lanes, snapshots artifacts, and manages the integration lane is a significant new subsystem. It touches context.rs, build.rs, and orchestrator.rs at minimum.
  • Cost model. Running 3 agents in parallel means 3x the API calls for that phase. The wall-clock savings may not justify the dollar cost for every project. This argues for keeping concurrency opt-in and defaulting to serial.
  • TUI observability. The terminal interface needs to show multiple lanes progressing simultaneously: per-lane status, blocked/unblocked transitions, integration merge results. A non-trivial UX challenge for a TUI.
  • Nested decomposition. v1 deliberately forbids nested lanes. But some projects have fractal structure -- an API lane might benefit from splitting into auth/data/search sublanes. This is a v2 concern at earliest.

Configuration

Concurrent workstreams are opt-in, configured per project in .foundry.json:

{
  "concurrent_workstreams": {
    "enabled": true,
    "max_lanes": 3,
    "contract_timeout_secs": 300,
    "integration_model": "opus",
    "lane_defaults": {
      "builder_model": "sonnet"
    }
  }
}

max_lanes caps simultaneous agents (cost control). contract_timeout_secs is how long a blocked lane waits before escalating. The integration agent uses the most capable model since it needs to reason about cross-cutting concerns and resolve semantic conflicts.

v1 Constraints

The first implementation keeps the corral tight:

  • Max 2-3 lanes (not counting integration)
  • No nested lanes
  • No overlapping ownership between lanes
  • Contracts are frozen once written -- no mid-flight amendments
  • Integration lane is always present and always owns shared files
  • Per-lane stages are Plan + Implement only -- no per-lane Scout or Doubt
  • One system-level Review pass after integration

These constraints loosen once the orchestration layer is trail-proven. The goal is to validate the model with the simplest possible implementation, then expand.

Summary

Concurrent Workstreams extends Foundry with three new primitives:

  1. Decompose -- a trail boss agent that splits work into bounded lanes with typed contracts and strict file ownership
  2. Loop Manifest -- a versioned JSON coordination protocol that governs parallel execution, artifact publishing, and dependency resolution
  3. Integration Lane -- a dedicated owner of shared files that merges at milestones, not just at the end, and runs build verification after each merge

The existing SPID stages run in simplified form within each lane (Plan + Implement). Scout runs once at the top. Doubt runs once at the bottom as a system-level Review. The integration lane operates continuously throughout parallel execution.

This is not "run N loops." It is one trail boss, bounded lanes, a dedicated integrator, and a single source of truth for what the merged herd looks like when it reaches the railhead. That matches how Foundry already thinks.
