## 1. Node Architecture Analysis

Analyze the detected Flowise flow structure:

- **Identify All Node Types**
  - LLM nodes (language model chains)
  - Agent nodes (AgentExecutor with reasoning)
  - Tool nodes (external integrations, APIs, databases)
  - Memory nodes (conversation history, context management)
  - Retriever nodes (vector stores, semantic search)
  - Input/Output nodes (user interface, data flow)

- **Map Data Flow Between Nodes**
  - Trace how data passes through the flow
  - Identify transformation points
  - Check for proper input/output connections
  - Verify data types are compatible

- **Check for Proper Error Handling**
  - Are there fallback nodes for failures?
  - Do LLM nodes have timeout configurations?
  - Are API calls wrapped with retry logic?
  - Is there graceful degradation?

## 2. Flow Quality Benchmarks (1000-Star Criteria)

High-quality Flowise flows exhibit these production-ready characteristics:

✓ **Production-Ready Error Handling**
  - Every external call has try/catch logic
  - Fallback responses defined for all failure modes
  - User-friendly error messages (not stack traces)
  - Logging for debugging without exposing secrets

✓ **Retry Logic Implemented**
  - LLM calls retry on rate limits (exponential backoff)
  - API integrations retry on transient failures
  - Maximum retry attempts configured (typically 3)
  - Circuit breaker pattern for repeated failures

✓ **Memory Management Patterns**
  - Conversation memory has size limits (not unbounded)
  - Old messages summarized or pruned
  - Separate short-term vs long-term memory
  - Memory cleared appropriately between sessions

✓ **Tool Integration Best Practices**
  - Tool descriptions clear and specific
  - Input schemas validated before execution
  - Tool outputs sanitized and validated
  - Rate limits respected for external APIs

✓ **Prompt Engineering Excellence**
  - System prompts are clear, specific, and tested
  - Few-shot examples included where helpful
  - Output format explicitly specified
  - Prompts tested with edge cases

## 3. Anti-Patterns to Identify

Flag these common Flowise mistakes for correction:

❌ **Circular Dependencies**
  - Agent A calls Agent B which calls Agent A (infinite loop)
  - Memory node feeding back into itself
  - Unguarded recursive tool calls

❌ **Missing Error Handlers**
  - No fallback for LLM failures
  - Unhandled API rate limits
  - No timeout configuration (hangs indefinitely)

❌ **Hardcoded Values in Prompts**
  - API keys in system prompts (security risk)
  - Hardcoded URLs (not configurable for environments)
  - Specific user names or data (not reusable)

❌ **Inefficient Token Usage**
  - Entire conversation history sent every request
  - Redundant context repeated in multiple prompts
  - No summarization for long conversations
  - Unnecessarily verbose system prompts

❌ **Poor Multi-Agent Design**
  - Too many agents (>5) causes routing confusion
  - Agents with overlapping responsibilities
  - No clear supervisor/coordinator
  - Shared state not properly synchronized

## 4. Architecture Recommendations by Flow Type

### For Multi-Agent Flows:
- **Supervisor Pattern**: One agent routes to specialized workers
- **Clear Boundaries**: Each agent has narrow, well-defined role
- **Shared Context**: Use memory for agent-to-agent communication
- **Error Recovery**: Supervisor handles worker failures gracefully
- **Avoid**: More than 5 worker agents, overlapping responsibilities

### For RAG (Retrieval-Augmented Generation) Flows:
- **Hybrid Search**: Combine semantic + keyword search
- **Reranking**: Post-process retrieval results for relevance
- **Chunk Size**: 512-1024 tokens optimal for most use cases
- **Embedding Cache**: Cache embeddings for performance
- **Fallback**: Respond gracefully when no relevant docs found

### For Workflow Flows:
- **Sequential Steps**: Clear linear progression
- **State Management**: Pass outputs to next step cleanly
- **Validation**: Check outputs before next step
- **Idempotency**: Steps can be safely retried
- **Progress Tracking**: User can see where flow is

### For Chatbot Flows:
- **Conversation Memory**: Buffer or summary memory
- **Context Window**: Monitor token usage, summarize when needed
- **Personality**: Consistent tone and style in prompts
- **Guardrails**: Input validation, content filtering
- **Session Management**: Clear memory between users

## 5. Testing Strategy for Flowise Flows

Scout should recommend these testing approaches:

**Unit Testing (Node-Level)**
- Test each node in isolation with mock inputs
- Verify node configurations (API keys, parameters)
- Check error handling paths
- Validate output format

**Integration Testing (Flow-Level)**
- Test node-to-node data passing
- Verify memory persistence across steps
- Check tool call sequences
- Test error propagation

**E2E Testing (Real LLM)**
- Test complete flow with actual LLM calls
- Use test API keys (not production)
- Verify conversation memory works
- Test edge cases (long inputs, special characters)
- Monitor token usage and costs

**Load Testing (Production Readiness)**
- Concurrent user simulation
- Rate limit validation
- Memory usage under load
- Response time benchmarks

## 6. Deployment Considerations

**Environment Variables**
- API keys (OpenAI, Anthropic, etc.)
- LLM model versions
- Temperature and max_tokens settings
- Feature flags

**Monitoring & Observability**
- Log all LLM calls (prompt + response)
- Track token usage and costs
- Monitor error rates by node type
- Alert on high failure rates

**Rate Limiting**
- Respect upstream API limits
- Implement per-user rate limiting
- Queue requests if needed
- Graceful handling when limits hit

**Security**
- Never log API keys or secrets
- Sanitize user inputs before LLM
- Validate tool outputs before showing user
- Implement content filtering
