Symphony vs Context Foundry vs Linear

Three pieces of the modern AI-coding stack — an orchestrator spec, a local pipelined builder, and an issue tracker. Side-by-side feature evaluation plus how they fit together.

TL;DR on roles: Symphony and Context Foundry are orchestrators — they run coding agents. Linear is a tracker — it stores tickets. Symphony was explicitly designed to use Linear as its work queue, so they're complements, not competitors. Context Foundry uses a local TASKS.md instead of any tracker.

What each one is

Symphony

OpenAI Apache-2.0 Elixir ~21k stars

A language-agnostic spec + reference daemon that turns a Linear board into the control plane for Codex agents. Polls a tracker, spawns one agent per ticket in an isolated workspace, runs until handoff (e.g. Human Review). Released as a "reference implementation" OpenAI does not plan to maintain as a product.

github.com/openai/symphony

Context Foundry

Local-first Rust MCP-aware Multi-provider

A local pipelined builder TUI that runs the RPID/QRPBA stages (Query → Research → Plan → Build → Audit) over a TASKS.md queue, with provider-agnostic model routing (Claude / Codex / Copilot CLIs), a pattern-learning store, and a fresh-context doubt loop.

/Users/Shared/homelab/context-foundry

Linear

SaaS Proprietary app MIT SDK Closed source server

A hosted issue tracker for software teams — projects, issues, states, branches, GraphQL API. The product itself is closed-source SaaS at linear.app (free tier + paid plans). The github.com/linear/linear repo is the public TypeScript SDK and tooling, MIT-licensed. You cannot self-host Linear — you sign up and connect to api.linear.app/graphql.

How Linear fits with Symphony

Symphony's SPEC pins tracker.kind: linear as the only currently supported tracker. The daemon authenticates with LINEAR_API_KEY, queries the GraphQL endpoint at api.linear.app/graphql, and walks every issue in the configured project_slug whose state is in tracker.active_states (defaults: Todo, In Progress). For each one, it spins up a workspace, launches a Codex session, and injects a dynamic linear_graphql tool so the agent can read and mutate the ticket directly — while keeping the API token out of sub-agent context.

In other words: Linear is the queue, Symphony is the worker pool, Codex is the worker. Without Linear (or a Linear-shaped adapter you write yourself), Symphony has nothing to poll.

Can I install Linear locally? No. Linear is closed-source SaaS — there is no on-prem or self-hosted edition. The linear/linear repo on GitHub is just the TypeScript SDK and tooling (codegen, import scripts, examples). To use Linear with Symphony you sign up at linear.app, create a workspace + project, generate an API key, and point Symphony at it. The free tier (250 issues, 10 users) is enough to evaluate.

Local-stack options if you don't want Linear

  1. Use Linear's free tier — fastest path; what Symphony was designed for.
  2. Stub a fake tracker — small GraphQL server mimicking the Linear schema Symphony queries; lets you exercise the orchestrator fully offline.
  3. Fork Symphony, add a new tracker.kind — the SPEC says additional tracker kinds are allowed; the reference impl just ships linear. A tracker.kind: github adapter that polls GitHub Issues, or tracker.kind: file that reads JSON from disk, would give you a fully local stack.
  4. Use Context Foundry instead — if a local TASKS.md queue is enough, you skip the tracker entirely.

Where Symphony and Context Foundry overlap

  • Both treat the workspace as the unit of isolation and run agents against a real filesystem checkout.
  • Both keep policy in the repo (Symphony's WORKFLOW.md, Foundry's CLAUDE.md / SPEC.md / TASKS.md).
  • Both are designed to decouple humans from individual agent sessions — humans set work, agents execute, humans review.

Where they fundamentally differ

  1. Axis of scale. Symphony scales horizontally across tickets (many agents, one Codex loop each). Foundry scales vertically through a single task (one task, many specialized stages with different models).
  2. Where intelligence lives. In Symphony, the smarts are inside Codex's own multi-step loop. In Foundry, the smarts are in the pipeline structure — Research feeds Plan, Plan feeds Build, Build feeds Audit, and patterns feed back into Plan on the next run.
  3. Verification model. Symphony defers verification to "human review" as a tracker state. Foundry bakes a fresh-context auditor into the pipeline and refuses to mark feat() (vs WIP()) unless Doubt passes.
  4. Provider posture. Symphony is Codex-shaped end to end. Foundry is provider-router-shaped — Opus on Plan, Codex on Build, a local LM Studio model on Research.
  5. Memory. Symphony has none. Foundry's pattern store is the whole point of the project's name.

Use-case fit

  • Pick Symphony if you have a Linear-driven team workflow, lots of well-scoped tickets, and want autonomous Codex agents grinding them down in parallel on a devbox.
  • Pick Context Foundry if you're a solo or small-team builder who wants stage-level control, multi-provider routing, an explicit audit gate, and accumulated learning across projects.
  • They're not really competitors. Symphony is a fan-out scheduler; Foundry is a depth-first builder with memory. You could plausibly run Foundry as the per-ticket coding agent inside a Symphony deployment.
